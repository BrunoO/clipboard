### High

**U1 — Failed database writes are discarded while success toasts are shown for "Mark as Secret" and delete**  
- **Flow / screen**: History view header actions and keyboard delete.  
- **Evidence**: `src/app/history_view.rs:157-168`:
  ```rust
  ItemAction::ToggleSecret(id, make_secret) => {
      let _ = self.db.set_item_secret(id, make_secret);
      if !make_secret {
          self.revealed_secrets.remove(&id);
      }
      self.refresh_items();
      let msg = if make_secret {
          format!("{} Marked entry as Secret.", icons::LOCK)
      } else {
          format!("{} Unmarked entry as Secret.", icons::LOCK_OPEN)
      };
      self.show_toast(&msg);
  }
  ```
  `src/app/history_view.rs:175-180`:
  ```rust
  ItemAction::Delete(id) => {
      let _ = self.db.delete(id);
      self.revealed_secrets.remove(&id);
      self.texture_cache.remove(id);
      self.refresh_items();
      self.show_toast(&format!("{} Entry deleted.", icons::TRASH));
  }
  ```
  Keyboard path has the same pattern at `src/app/mod.rs:733-746`:
  ```rust
  let id = item.id;
  let _ = self.db.delete(id);
  self.texture_cache.remove(id);
  self.refresh_items();
  ```
- **User-visible problem**: A privacy-critical state change ("Marked entry as Secret") and both deletion paths report success even if `Database::set_item_secret` (`src/db.rs:579`) or `Database::delete` (`src/db.rs:614`) returned `Err`. The user can believe an item is masked or removed when it is not.
- **Recommendation**: Match on the `Result`: show a warning toast with a short, non-raw error summary on failure, skip the local `revealed_secrets`/cache mutations and the success toast, and only call `refresh_items()` after a successful write. Apply the same handling to `delete_filtered_item`.
- **Verification**: Add a unit test with an injected/failing database mock for each action, or manually force a read-only/locked database and confirm the warning toast appears and the row remains.

### Medium

**U2 — Warning and error toasts are rendered in the success color**  
- **Flow / screen**: Bottom status panel after clipboard or browser failures.  
- **Evidence**: Failure messages are created at `src/app/mod.rs:434` and `src/app/mod.rs:439-442`:
  ```rust
  self.show_toast(&format!("{} Clipboard unavailable", icons::WARNING));
  ```
  ```rust
  self.show_toast(&format!(
      "{} Failed to copy text to clipboard",
      icons::WARNING
  ));
  ```
  All toasts are rendered identically at `src/app/mod.rs:1097-1103`:
  ```rust
  if let Some((msg, time)) = &self.toast {
      if time.elapsed() < Duration::from_secs(2) {
          ui.label(
              egui::RichText::new(msg)
                  .color(crate::theme::success_color(is_dark))
                  .strong(),
          );
  ```
- **User-visible problem**: "Clipboard unavailable", "Failed to copy", and "Blocked invalid URL" messages are styled green/success despite their warning icon and text. That contradicts the message content and weakens error feedback.
- **Recommendation**: Change `toast: Option<(String, Instant)>` (`src/app/mod.rs:153`) to carry a severity (`Info`/`Warning`/`Error`) and select `success_color`, `warning_color`, or an error color at render time; keep the existing icon and text so status is not conveyed by color alone.
- **Verification**: Trigger a clipboard-unavailable state and a successful copy in one session and confirm distinct styling plus unchanged wording.

**U3 — First-run keyring explanation asserts OS-keyring storage even when local fallback is active**  
- **Flow / screen**: First-run "Secure Key Storage" modal.  
- **Evidence**: `src/app/mod.rs:1331-1336`:
  ```rust
  "To keep your clipboard history encrypted, CipherClipboard stores a \
   256-bit encryption key in your operating system's secure credential \
   store (macOS Keychain, Windows Credential Manager, or Linux Secret \
   Service). You may see an OS permission prompt the first time this \
   happens. This prompt will not appear again unless you reinstall or \
   reset the app.",
  ```
  The app already knows the actual mode; `src/app/mod.rs:1116-1122` renders:
  ```rust
  crate::crypto::KeyStorageMode::LocalFileFallback => {
      format!(
          "{} {} entries • Local key file (keyring unavailable)",
          icons::WARNING,
          self.items.len()
      )
  }
  ```
- **User-visible problem**: A user in `KeyStorageMode::LocalFileFallback` is told their key is in the OS keyring. The persistent bottom-panel status and Settings banner (`src/app/settings_view.rs:453-462`) are correct, but the first-run modal gives contradictory reassurance at the moment trust is being established.
- **Recommendation**: Branch the modal text on `self.key_storage_mode` (available on `ClipboardApp`, `src/app/mod.rs:147`): for fallback, state that the OS keyring was unavailable and that a restricted local `.encryption_key` is in use, with the same warning styling as the status bar.
- **Verification**: Launch with a mocked unavailable keyring (or use the existing test-mode key path) and confirm the modal and status bar agree.

### Low

**U4 — Keyboard selection is reset to the top on background capture, search edits, and window reopen [Inferred]**  
- **Flow / screen**: History list navigation with ↑/↓ or Ctrl+N/P and the number shortcuts.  
- **Evidence**: `src/app/mod.rs:865-876`:
  ```rust
  if new_items_detected || self.search_query != self.last_query_cached {
      self.refresh_items();
      self.last_query_cached = self.search_query.clone();
      self.selected_index = 0;
      self.scroll_to_selected = true;
  }
  ```
  `src/app/mod.rs:304-311`:
  ```rust
  fn show_window(&mut self, ctx: &egui::Context) {
      crate::logging::log_message("INFO", "show_window called");
      self.is_visible = true;
      self.has_been_focused = false;
      self.was_inactive_since_hidden = false;
      self.selected_index = 0;
      self.show_clear_confirm_dialog = false;
      self.scroll_to_selected = true;
  ```
- **User-visible problem**: [Inferred] A user who navigates to an older entry loses that position whenever a new clipboard item arrives, the search text changes, or the window is summoned again; the UX prompt asks that selection survive refresh and hide/show.
- **Recommendation**: Preserve selection by item id across refresh and only clamp it when the selected id disappears; on `show_window()`, restore the last selection unless the filter changed. Keep the existing reset for an explicit "Clear All" or first load.
- **Verification**: Navigate to row N, trigger a background copy, hide/show with the hotkey, and confirm the same row remains selected and scrolled into view.
